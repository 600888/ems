# EMS 实时数据与配置

本文描述 C++17 采集、实时数据库、存储、策略与 Drogon Web 五类进程中的实时数据边界。整体决策以[系统架构](../../architecture/system-design.md)为准，实时生命周期见[实时数据库进程设计](../../processes/data/design.md)，采集执行见[数据采集架构](../../processes/collector/design.md)。以下为目标设计，不代表代码已完成实现。

公共实时状态统一通过 `IRealtimeStore` 抽象基类及业务门面访问，支持共享内存、Redis 与其他满足契约的内存数据库派生类，详细定义见 [公共实时数据访问接口设计（C++17）](access-design.md)。Redis 为默认实时后端，只保存实时状态；配置以 MySQL 为权威，消息传输走 ZeroMQ。

`ems-rtdb` 在所有后端下均常驻，按统一配置选择和管理后端。业务只使用 `RealtimeClient`，不解析 Redis 地址、共享段名或后端类型；公共客户端内部发现部署、选择适配器并直接访问后端。后端扩展保持同一业务 API，配置切换通过受控维护完成；正常读写不经管理 RPC。

消息订阅与命令下发使用独立于状态后端的 [ZeroMQ 通道](zeromq-messaging-design.md)：PUB/SUB 提供可丢弃的变更提示，REQ/REP 配合 MySQL 持久状态交接命令。旧采集分发器已提供可选通知接入；命令业务入口仍待接线。

键命名以独立文档 [Redis 键设计](redis-key-design.md) 为准：储能单元 code 全局唯一，测点键以 `ems:rt:point:` 开头，再接 `{<unit_code>}`、逐级设备 code 和测点 code；站级公共测点使用 `ems:rt:point:{station:<station_code>}:...`。其他资源使用 `ems:{<unit_code>}` 或 `ems:{station:<station_code>}` 加资源路径。站标识统一使用 station，消息保留 station_id/code 和稳定资产 ID。

## 1. 数据职责

| 数据 | 权威存储与访问方式 |
| --- | --- |
| 实时最新值、质量、设备/通道状态 | 经统一接口访问选定权威后端；Redis 默认使用 Hash，共享内存使用有版本的完整记录，由采集与对应状态所有者更新 |
| 历史采样 | 独立 ZeroMQ 遥测 PUB/SUB 传递完整原始事件；允许丢样，存储进程写时序库 |
| 控制意图、执行命令和回执 | MySQL 持久记录与 outbox/inbox；命令经 ZeroMQ REQ/REP 交接，结果变化经 PUB/SUB 唤醒并查询权威记录 |
| 资产、通道绑定、点表、配置版本和业务审计 | MySQL；各 C++ 进程通过公共 ormpp API 按业务职责访问，每个进程独立管理连接或连接池 |
| 时序值与聚合结果 | 存储进程通过统一后端接口写入和查询，首期实现 TDengine 3.4.2 |
| 配置分发 | MySQL 保存完整版本；ZeroMQ 提示各进程按版本重读并反馈应用状态 |

进程本地配置缓存用于加速访问。各进程通过公共实时库、版本化消息与管理/历史 gRPC 协作；同机受信任的 C++ Web 后端直接读取共享段或 Redis，浏览器只访问 Web，不继续默认由存储代理实时查询。共享段切换必须停止并隔离旧使用者，不能读取未同步的另一后端。连接、连接池与事务句柄归各进程独立所有。告警规则、聚合和控制仲裁仍属于策略进程。

## 2. 实时值与遥测事件

采集进程生成包含测点、设备、通道、来源代次、序号、类型、值、单位、质量及时间的遥测记录。Redis 最新值按 `source_epoch/sequence` 判定更新顺序，新鲜度通过 `stale_after` 和质量表达。

采样先进入有界内存队列，再分别更新最新值和通过独立 ZeroMQ 主题发布完整原始事件，不提供本地文件持久缓冲。存储进程接收后按稳定 `event_id` 核验并写入时序库。PUB/SUB 没有 ACK、待处理接管或重放；发布者离线、进程重启、队列溢出或数据库故障均可能形成历史缺口。

ZeroMQ PUB/SUB 同时用于可丢失的变化提示和独立的原始遥测主题，两类载荷不能混用；命令使用独立 REQ/REP 通道。历史事件投递、失败边界与跨进程字段约定见整体架构第 5 节。

## 3. 控制闭环

上送通道收到的外部控制由通信进程校验 peer、control_in、标准命令映射与版本，再经公共 ormpp API 将意图和 outbox 同事务持久保存；与 Web/自动意图使用同一策略仲裁链路。监听器或协议回调不得直接写南向设备。通道关系及北向确认语义见 [设备、通道与协议](../../architecture/channel-protocol.md)。

Drogon Web 通过公共 ormpp Repository 将人工意图与 outbox 同事务写入 MySQL；策略通过公共 ormpp API 持久保存自动意图。人工或自动意图经过策略进程统一仲裁，再由策略将执行命令与 outbox 同事务保存。outbox 发布器通过 ZeroMQ REQ/REP 交给采集持久 inbox，超时按同一 `command_id` 查询或重试。采集进程校验有效期、配置版本、控制权代次与互锁，在通道事务边界执行，通过公共 Repository 条件登记 MySQL 执行状态后再写设备并回读验证；登记失败不执行，回执与 outbox 同事务保存。

命令回执以 MySQL 记录持久审计，ZeroMQ 仅通知状态变化。以 `command_id` 关联幂等记录、协议确认和设备反馈；超时或不确定结果按整体架构第 6 节处理。

## 4. 点表与配置发布

1. Vue 页面先选择实际设备，导入厂家点表草稿，按设备类型将厂家点绑定到固有点位，显式禁用不支持项；Web 完成权限、语义、路由与能力依赖校验。
2. Web 通过公共 ormpp Repository 在本进程的 MySQL 事务内保存资产、设备与通道绑定、厂家路由、标准映射与禁用状态、配置版本和 outbox；其他进程发起的配置变更遵循相同事务与版本规则。
3. MySQL 保存完整配置版本，ZeroMQ 发布变更提示；采集和策略从 MySQL 加载指定版本并反馈应用状态。
4. 页面分别展示已保存、已发布和各实例已应用的版本；配置不一致时拒绝依赖新映射的控制。

测点业务身份独立于通信路径。一个设备可绑定多个通道，多台设备可通过不同从站地址共享通道；完整模型见整体架构第 3、4 节，公共数据库 API、独立连接与事务约束见第 7 节。

固有点位目录、厂家差异转换、重复导入、模板升级及命令反馈规则见 [EMS 设备模型与点表绑定设计](../../architecture/device-model.md)。选定的权威实时后端保存标准逻辑值；禁用/未配置项不输出默认零值，命令点不通过写实时测点键触发执行。

## 5. 实施与验收

按整体架构第 10 节落实跨进程契约、配置发布、实时数据分发和控制审计。验收覆盖重复事件、ZeroMQ 断线及数据库故障时的可观测丢样、来源切换、配置版本不一致、多设备共享通道和控制执行结果核对。
