# EMS 实时数据与配置

本文描述 C++17 采集、存储、策略与 Go Web 四类进程中的实时数据边界。整体决策以 [EMS 系统架构设计](../../architecture/system-design.md) 为准，采集执行细节见 [数据采集架构](../../processes/collector/design.md)。以下为目标设计，不代表代码已完成实现。

公共实时状态统一通过 `IRealtimeStore` 抽象基类及业务门面访问，支持共享内存、Redis 与其他满足契约的内存数据库派生类，详细定义见 [公共实时数据访问接口设计（C++17）](access-design.md)。Redis 为默认部署后端；本文涉及 Redis 最新值的描述属于该默认实现。可靠事件、配置快照与实时状态分别选择实现，共享内存模式不会自动替换 Redis Streams 或配置仓储。

键命名以独立文档 [Redis 键设计](redis-key-design.md) 为准：储能单元 code 全局唯一，测点键以 `ems:rt:point:` 开头，再接 `{<unit_code>}`、逐级设备 code 和测点 code；站级公共测点使用 `ems:rt:point:{station:<station_code>}:...`。其他资源使用 `ems:{<unit_code>}` 或 `ems:{station:<station_code>}` 加资源路径。站标识统一使用 station，消息保留 station_id/code 和稳定资产 ID。

## 1. 数据职责

| 数据 | 权威存储与访问方式 |
| --- | --- |
| 实时最新值、质量、设备/通道状态 | 经统一接口访问选定权威后端；Redis 默认使用 Hash，共享内存使用有版本的完整记录，由采集与对应状态所有者更新 |
| 历史采样、告警、控制意图、执行命令和回执 | Redis Streams 可靠传递，由独立消费组处理 |
| 资产、通道绑定、点表、配置版本和业务审计 | MySQL；Go 使用 GORM，C++ 各进程通过公共 ormpp API 按业务职责访问，每个进程独立管理连接或连接池 |
| 时序值与聚合结果 | TDengine，由存储进程写入和查询 |
| 配置分发 | 存储进程发布 Redis 版本快照，缺失时 C++ 进程通过公共 ormpp API 从 MySQL 加载指定版本 |

进程本地缓存用于加速访问。C++ 与 Go 通过统一数据库结构、版本化消息、Redis 数据结构和 gRPC 协作；共享内存部署的 Go 实时查询经存储进程内的实时查询 gRPC，不能继续读取未同步的 Redis。C++ 公共模块复用数据库 API 代码，连接、连接池与事务句柄归各进程独立所有。告警规则和控制仲裁属于策略进程。

## 2. 实时值与可靠事件

采集进程生成包含测点、设备、通道、来源代次、序号、类型、值、单位、质量及时间的遥测记录。Redis 最新值按 `source_epoch/sequence` 判定更新顺序，新鲜度通过 `stale_after` 和质量表达。

采样先进入有界内存队列，再分别更新最新值和发布采样 Stream，不提供本地文件持久缓冲。存储消费者使用 Stream 中的原始采样入库，目标数据库确认后才 XACK；重复投递按稳定 `event_id` 去重。待处理接管、背压和裁剪以必需消费者进度为依据。Streams 接受后可释放发布缓冲；进程重启或缓冲耗尽时，未发布采样可能丢失并形成历史缺口。

Pub/Sub 仅用于允许丢失的页面刷新或缓存失效提示。事件投递、失败恢复边界与跨语言字段约定见整体架构第 5 节。

## 3. 控制闭环

上送通道收到的外部控制由通信进程校验 peer、control_in、标准命令映射与版本，再经公共 ormpp API 将意图和 outbox 同事务持久保存；与 Web/自动意图使用同一策略仲裁链路。监听器或协议回调不得直接写南向设备。通道关系及北向确认语义见 [设备、通道与协议](../../architecture/channel-protocol.md)。

Go 通过 GORM 将人工意图与 outbox 同事务写入 MySQL；策略通过公共 ormpp API 持久保存自动意图。人工或自动意图经过策略进程统一仲裁，再由策略将执行命令与 outbox 同事务保存。存储进程统一发布已提交的 outbox。采集进程校验有效期、配置版本、控制权代次与互锁，在通道事务边界执行，通过公共 Repository 条件登记 MySQL 执行状态后再写设备并回读验证；登记失败不执行，回执与 outbox 同事务保存后 ACK。

命令回执通过独立 Stream 分发并持久审计。以 `command_id` 关联幂等记录、协议确认和设备反馈；超时或不确定结果按整体架构第 6 节处理。

## 4. 点表与配置发布

1. Vue 页面先选择实际设备，导入厂家点表草稿，按设备类型将厂家点绑定到固有点位，显式禁用不支持项；Go 完成权限、语义、路由与能力依赖校验。
2. Go 通过 GORM 在本进程的 MySQL 事务内保存资产、设备与通道绑定、厂家路由、标准映射与禁用状态、配置版本和 outbox；C++ 发起的配置变更通过公共 ormpp API 遵循相同事务与版本规则。
3. 存储进程发布 Redis 版本快照与配置变更，采集和策略加载完整版本并反馈应用状态。
4. 页面分别展示已保存、已发布和各实例已应用的版本；配置不一致时拒绝依赖新映射的控制。

测点业务身份独立于通信路径。一个设备可绑定多个通道，多台设备可通过不同从站地址共享通道；完整模型见整体架构第 3、4 节，公共数据库 API、独立连接与事务约束见第 7 节。

固有点位目录、厂家差异转换、重复导入、模板升级及命令反馈规则见 [EMS 设备模型与点表绑定设计](../../architecture/device-model.md)。Redis 发布标准逻辑值；禁用/未配置项不输出默认零值，命令点不通过写实时测点键触发执行。

## 5. 实施与验收

按整体架构第 10 节落实跨语言契约、配置发布、实时数据分发和控制审计。验收覆盖重复投递、Redis/数据库中断补传、来源切换、配置版本不一致、多设备共享通道和控制执行结果核对。
