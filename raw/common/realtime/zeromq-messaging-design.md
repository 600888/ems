# ZeroMQ 通知与实时库命令协作

实际控制入口与部署方式见[遥控与遥调](../../processes/collector/commands.md)。
控制命令统一先调用实时库接口写入，再发布通知；采集进程收到通知后读取实时库并执行。
策略的业务仲裁、互锁和控制权管理仍须由业务层完成。

## 1. 数据职责

| 路径 | 数据通道 | 通知与恢复 |
| --- | --- | --- |
| 测点最新值、质量、设备状态 | 公共实时库接口 → 共享内存 / Redis | 可选 PUB/SUB 提示，消费者重读实时库 |
| 控制命令目标与状态 | `CommandClient` → 实时库独立命令记录 | 写入后发 `command.pending`，消费者认领后执行；扫描补偿丢提示 |
| 命令执行结果与持久去重 | 采集侧 MySQL `ops_command` → 实时库同步 | 各进程通过实时库查询 |
| 原始历史采样 | 独立 telemetry PUB/SUB → 存储进程 | 传递完整样本，允许离线、高水位与故障丢样，无 ACK 或重放 |
| 配置变更 | MySQL 原地保存并递增站根 `config_revision` | 消费者比对修订号后重建运行目录 |

```mermaid
flowchart LR
    Caller[Web / 策略 / 命令行] --> API[CommandClient.submitCommand]
    API --> RT[(统一实时库 Pending)]
    API -.写入完成后提示.-> PUB[PUB 连接]
    PUB -.command.pending / 只有 ID.-> SUB[采集 SUB 绑定]
    SUB --> Read[读取实时库并认领]
    RT --> Read
    Read --> DB[(MySQL 条件执行登记)]
    DB --> IO[原通道线程 / 协议下发]
    IO --> Result[(MySQL 结果)]
    Result --> RT
```

通知端点不受理命令目标，不返回执行结果。现有通用 REQ/REP 传输类仍保留用于独立传输测试，
Web、`ems-command` 和 `ems-collector` 的实际控制链路不再使用它们。

## 2. PUB/SUB

### 2.1 变更提示

`ZmqChangePublisher` 由专用线程独占 PUB socket，业务线程只向有界队列提交提示。
`ZmqChangeSubscriber` 独占 SUB socket，按完整主题加 NUL 精确过滤。
单帧编码为 `<topic> NUL <正文>`，默认最大 64 KiB，应用队列和高水位默认各 1024。
测点提示正文可以是测点 JSON；命令就绪提示正文只含 `command_id`。

`ZmqChangeConfig::publisher_bind` 默认为 true，适用于一个生产者向多个订阅者发布测点提示。
命令就绪使用 false：唯一采集执行者的 SUB 绑定，多个调用进程的 PUB 连接同一端点。
生产者在实时库条件写入成功后才发布 `command.pending`。
当前通知端点用于采集侧唤醒；执行状态和结果直接读取实时库，不依赖订阅。

PUB 入队成功不代表任何订阅者收到；晚加入、断线、高水位和关闭发布器都可能丢提示。
采集订阅回调只登记命令 ID 并唤醒调度，不在回调线程访问数据库或协议句柄。
主循环优先检查提示中的 ID，并周期执行有界扫描，启动时还会对账实时记录与持久未决记录。
因此通知重复不会重发动作，最后一条通知丢失也不需要等待下一条消息才能发现命令。

### 2.2 原始遥测

采集端发布独立的 `telemetry` 主题，正文是完整的版本化 `EventEnvelope` JSON，包含稳定 `event_id`、站/单元作用域、配置版本、源时间和有类型的测点值。主题携带受控作用域，存储端还须核对信封内作用域；旧四遥变更提示 JSON 不含这些历史身份字段，不能转作原始遥测。存储接收线程检查帧边界并提交有界队列；工作线程通过[公共数据库访问层](../database/)读取历史版本、事务登记事件身份，再调用公共时序接口，业务不直调 ormpp/驱动。首期 TDengine 3.4.2，InfluxDB 后续适配。

原始遥测 PUB/SUB 与变更提示同样允许丢失。发布端本地入队成功不表示存储已接收；订阅者晚启动或断线、发送或接收高水位、存储进程队列溢出、MySQL 或时序库故障，都可能形成无法自动补回的历史缺口。此通道不提供 ACK、pending、消费组或重放游标。存储进程的 MySQL `history_event_identity` 和隔离记录只覆盖实际收到的事件，不能推断未收到样本的内容。监控应同时报告发布拒绝、接收队列丢弃、数据库写入失败、来源序号跳变和采样静默；序号只能检测部分缺口，不替代端到端投递证明。恢复时从新样本继续，不能用 Redis 当前值伪造缺失历史。

## 3. 实时库命令闭环

1. 调用方调用 `CommandClient::submitCommand`，将稳定 ID、点 ID、工程值、期限和
   `config_revision` 条件创建为 Pending；同 ID 同载荷返回已有状态，异载荷返回冲突。
2. 库内部在写入成功后发布就绪提示。通知失败不撤销命令，也不允许换 ID 重发。
3. 采集侧读取实时记录，校验期限、当前配置与路由，写入持久 `ops_command`。
4. 通道线程在事务边界将实时状态 CAS 认领为 Executing，再条件登记 MySQL 执行身份。
   认领冲突、登记失败、登记结果未知或期限已过时，不开始设备写入。
5. 协议确认与反馈核验结果先持久保存，再同步写回实时库。同步失败保留待补同步项；
   重启对账既有实时记录并将旧 Executing 持久记录变为 Unknown，不自动重发可能执行的动作。
6. Web 和其他进程调用 `readCommand` 查询结果；显式核验仅在实时记录中登记核验请求，
   采集侧只读设备反馈，不重新写入原目标。

命令目标、命令状态和 YC/YX 实际反馈各自保存。协议确认不等于实际反馈已经达到目标。
Pending 只证明实时库写入成功，持久受理发生在采集侧登记后。共享内存整体丢失可能丢掉
尚未持久登记的 Pending；已执行命令的持久去重不能随实时记录清理而删除。

## 4. 部署与故障

采集和生产者必须挂接同一实时库后端、使用相同站级 scope，并配置相同通知端点。
共享内存仅限同机；业务代码通过公共客户端访问，不直接传共享内存指针。
每个 scope 只部署一个执行实例。示例通知端点为 `tcp://127.0.0.1:5558`，它不再接受旧
`EMS-CMD/1` 请求。通知端点为空时使用扫描，不启用 ZeroMQ 的构建也可采用该方式。

| 故障 | 行为 |
| --- | --- |
| 实时库写入失败 | 不发布就绪提示，返回明确错误；写入结果未知时按原 ID 查询 |
| 通知断线、迟到或重复 | 扫描补偿，执行前重新读取实时记录并检查期限；不根据消息载荷执行 |
| 执行登记失败或未知 | 不进行设备写入，重新读取持久事实后收敛状态 |
| 执行结果暂时无法同步实时库 | 保留待补同步项，恢复后按持久事实修复，不重新执行动作 |
| 采集在设备 I/O 期间退出 | 旧 Executing 记为 Unknown，只核验新反馈 |
| 实时库容量耗尽 | 拒绝新提交，当前不自动清理命令记录；维护时保留持久去重 |
| 原始遥测订阅离线 | 中间样本可能丢失，不能用实时最新值伪造缺失历史 |

通知和实时库的写入不构成跨系统事务，周期扫描是必要的补偿机制。当前部署面向可信本机
调用方，消息库没有额外远程认证；跨主机服务须独立验证身份与传输边界。

## 5. 构建与验证

```sh
cmake -S backend -B backend/build/linux-native -DEMS_WITH_ZEROMQ=ON
cmake --build backend/build/linux-native --target ems_rtdb ems-collector ems-command
```

Windows 预设默认启用 ZeroMQ，使用仓库内 libzmq 源码构建。
测试覆盖独立命令存储、多个生产者先写后通知、丢通知扫描、重复提交、CAS 认领竞争、
过期、配置修订号变化、数据库登记失败、未知执行和重启状态补同步。
