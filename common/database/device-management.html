    #设备管理数据库表设计

    日期：2026-10-24｜状态：表结构已落为 003 迁移，仓储与首期 Web 接口已实现 依据：.pen/device_manage.pen 全部 9 个页面、公共模型设计、实时访问接口设计 迁移：backend/data/migrations/003_device_management_mysql.sql + backend/data/seeds/device_management_seed.sql（旧 42 表设计已被本设计取代，脚本原地改写）

    Web 用例与保存边界见设备模块设计，HTTP 载荷见设备模块 API。下文定义持久化模型；本次已补齐公共分页/锁查询、模板读取和导入仓储；运行及测试边界见构建运行。

    #0. 本次重构结论

    问题前版做法本文做法
    资产与设备两套概念cfg_asset + cfg_device 双主键，部件点还要 device_id NULL只有一张 cfg_device 设备树，node_kind 区分组织节点与设备节点
    四遥被拆散point_kind=telemetry/status/event/command，遥调并入 commandcfg_point_yc/yx/yk/yt 四张表，代码对应 YcPoint/YxPoint/YkPoint/YtPoint 四类
    一个物理量写三张表厂家点 + 标准点 + 路由 + 转换每类一张表：semantic_code 为空即扩展点，转换/命令/反馈内联为列
    派生状态建表固有点三态、能力、地址占用各建表三态由点行推出；能力由 capability_codes_json 聚合；地址区间保存时即时计算
    版本体系cfg_version + 草稿/复制/发布/快照/回执/差异开发阶段不需要版本：表可原地改，保存即生效，热加载靠站根 config_revision

    表数：14。

    #1. 目标与边界

    范围内

    • 一棵设备树：站 → 储能单元 → 通信设备 → 部件（电池系统/簇/包/电芯），以及站级公共设备。
    • 设备类型、固有点目录（四遥）、型号模板复用。
    • 通道（连接）与设备-通道绑定，采集/控制/转发角色。
    • 四遥点：协议地址、取值转换、命令写入规则、反馈判据、固有点映射。
    • 点表导入（逐行预览、地址基准、逐项确认、幂等重放）。
    • 配置保存后热加载：config_revision 单调递增，消费者轮询比对。
    • 与实时库配套的 5 分钟通信统计、设备/通道状态变化历史。

    范围外

    • 历史数据（TDengine 超级表，见 002_storage_taos.sql）与告警业务表。
    • 用户、角色、操作审计：归统一审计/权限模块，本设计不建 audit_log。
    • 北向转发映射（原 cfg_forward_map）：归通信管理模块，等该模块设计确认后再建表。
    • 采集驱动、策略算法、控制仲裁本身的行为。
    • 旧四遥表删除：过渡期保留只读，按第 9 节迁移。

    #2. 三个核心约定

    #2.1 只有设备，没有资产

    设计图上不存在“资产”入口，也没有“资产详情”页面。因此删除 cfg_asset、cfg_ess_unit，不再有 asset_id/asset_type/asset_path：

    node_kind含义能否绑通道能否挂点页面表现
    station站根节点，全树唯一；承载站点级默认值否否层级树根
    unit储能单元否否“储能单元 01 · 12 项”
    device通信设备（PCS/BMS/空调/消防/电表/保护/环控）是是有“通道绑定”“点表导入”页签
    component部件（电池系统/簇/包/电芯）否是类型列显示“层级”，详情显示“经 bms01 采集”
    • 部件节点不能自己通信，source_device_id 指向采集它的通信设备，正是页面 08 的 bms01 → rack01。
    • device_id 是文本稳定 ID，跨重复导入不变；数字自增主键只用于连接，不对外。
    • 站点级默认值放在站根行：timezone、default_stale_after_ms、config_revision。不单独建 cfg_scope。

    #2.2 四遥是点的唯一分类，四张表 + 四个类型

    表C++ 类型语义特有字段
    cfg_point_ycmodel::YcPoint遥测（上行模拟量）倍率、偏移、量程、死区
    cfg_point_yxmodel::YxPoint遥信（上行离散量，含 SOE）soe、invert、枚举码表
    cfg_point_ykmodel::YkPoint遥控（下行离散量）write_mode、固定值、脉冲、写组
    cfg_point_ytmodel::YtPoint遥调（下行模拟设定）工程值换算、可写量程、写组
    • 方向由表决定，不存在 access_mode 列，因此不会有“遥测点可写”这种数据。
    • 遥信变位/事件顺序记录不是第五类：仍属遥信，用 soe 标记，告警业务另表处理。
    • 页面 05 的分页签是“遥测/遥信/遥控/遥调”；原来的“事件 N”归入遥信并显示 SOE 角标。
    • 固有点目录 cfg_type_point 仍是一张表：四种类型的目录字段完全同构，拆开只是复制四份；能力归属用 capability_codes_json 表达多对多。

    代码侧与表一一对应：

    • 四个类型共享 model::PointBase（点 ID、设备节点、编码、名称、四遥分类、记录种类、值类型、单位、启用、反馈引用），基类构造函数 protected，只有四个具体类型能创建，point_type 与 kind 不可能不自洽。
    • ModelCatalog 持有 points_yc/points_yx/points_yk/points_yt 四个集合，for_each_point 遍历，find_point 返回 const PointBase*；索引存“类型 + 下标”，目录拷贝后索引仍有效。
    • 运行目录 RuntimePoint 保持单一结构但带 point_type：实时记录对四遥是同构的（值、质量、序号、时间），拆开只会让 findPoint 返回变体。

    #2.3 直接改工程表，不做版本

    开发阶段配置还在反复调整，不需要草稿/发布/快照/回滚。约定：

    • 页面“保存”直接 INSERT/UPDATE/DELETE 工程表，事务提交即生效。
    • 每次保存成功后，站根 cfg_device.config_revision + 1（同一事务内）。采集、策略、实时库等消费者按固定周期读该值，发现变化就重编运行目录并热切换，不重启进程。
    • config_revision 是缓存失效令牌，不是业务版本号：不提供历史查询、差异对比、回滚到旧版本。需要追溯时查统一审计日志。
    • 页面 06 从“发布 v13 / 差异预览 / 应用回执”收敛为“保存校验结果 + 各服务已加载的 revision”：校验不通过拒绝保存，不再有“草稿不影响运行”的状态。

    #5. 逻辑模型

    要点：

    • cfg_device 自引用成树，根 parent_device_id 为空串且 node_kind='station'，深度 ≤ 8（与实时库 RecordKey.device_path 上限一致）。
    • 四张点表都同时挂两个维度：owner_device_id（点归属节点，可以是部件）+ binding_id（实际采集来源）。部件点因此不需要虚构通信设备，也不需要路由表。
    • 一个设备可有多条绑定（采集口与控制口分开），但同一设备+同一通道只允许一行；采集/控制/转发用标志位表达。

    #6. 核心表字段语义

    完整列定义以 003 迁移为准，这里只写有决策含义的字段。

    #6.1 cfg_device（设备树）

    字段说明
    device_id稳定设备 ID，全树唯一
    parent_device_id父节点；站根为空串（不用 NULL，唯一键才能约束根节点）
    node_kindstation/unit/device/component
    code同父节点下唯一
    path相对站根的路径，如 /unit01/battery01/rack01；实时库记录键的来源
    depth0–8，CHECK 约束
    device_type_code/type_version类型引用；device/component 必填，站与单元为空
    template_id创建时套用的型号模板，仅记录来源
    source_device_idcomponent 必填，指向采集它的通信设备
    vendor/model/firmware_version/rated_power_kw设备档案字段
    timezone/default_stale_after_ms/config_revision仅站根使用：时区、点默认时效、热加载令牌
    enabled配置启用，与运行在线状态无关
    legacy_ref旧四遥表数字 ID

    唯一键：(device_id)、(parent_device_id, code)、(path)。

    #6.2 cfg_device_type（设备类型）

    (type_code, type_version) 复合主键，如 pcs + pcs-v1；category 供页面分组；status 支持停用。不随设备复制。

    #6.3 cfg_type_point（类型固有点目录）

    字段说明
    (type_code, type_version, semantic_code)主键；如 active_power、run_state、start
    point_typeyc/yx/yk/yt，决定映射行必须落在哪张点表
    value_type/unit与实例比对，不一致拒绝保存
    required属于任一能力即为必需；必需固有点未映射时阻止保存
    capability_codes_json所属能力数组，如 ["monitor_power","set_active_power"]
    writable仅 yk/yt 允许为真，CHECK 约束
    stale_after_ms0 表示继承站默认

    能力不单独建表，页面 02 的能力状态由固有点聚合：

    页面状态判定
    可用capability_codes_json 含该能力的全部 required=1 固有点均为“已启用”
    不可用任一必需固有点为“已禁用”，展示其 disabled_reason
    未配置存在必需固有点没有任何映射行

    #6.4 cfg_template（型号模板）

    (template_id, template_version) 主键，points_json 保存默认四遥点表与映射。模板是“复制源”，不参与运行期联表，所以用 JSON 一次存全。套用模板时由服务按固有点类型生成对应点表的行；模板里的地址只是建议值，绑定通道不同需重填。

    #6.5 cfg_channel（通道）

    channel_id 稳定 ID，code 唯一；protocol + conn_mode + endpoint + serial_json 描述连接；poll_interval_ms/timeout_ms/retry_times 是采集参数；max_sessions 表达共享连接上限。

    共享通信资源不单独建表：一条通道就是一条物理连接，多个设备绑同一通道即共享，绑定表已能回答“谁在共用”。

    #6.6 cfg_binding（设备-通道绑定）

    字段说明
    binding_id稳定绑定 ID，ops_comm_stat_5m 的统计维度
    device_id + channel_id联合唯一
    device_addressUnit ID / 公共地址 / 从站号
    profile_version协议 Profile，如 mbtcp-v3
    can_collect/can_control/can_forward角色标志，三者至少一个，CHECK 约束
    enabled绑定级开关

    页面 03 的“主采集 · ch01”“控制下发 · ch01”两行是同一绑定的两个角色视图，不再按角色重复建行。采集与控制若走不同连接，绑两条不同通道即可。

    #6.7 四遥点公共列

    四张表前 17 列同义：

    字段说明
    point_id稳定点 ID；四表之间也全局唯一（服务校验，单表唯一键表达不了）
    owner_device_id点归属节点；部件点填 rack/pack/cell
    binding_id实际采集来源绑定；部件点填 BMS 的绑定
    code/name业务编码与显示名；code 同归属节点唯一
    semantic_code非空=固有点映射；空=厂家扩展点（只采集诊断）
    vendor_key厂家点稳定键，重复导入据此更新；(binding_id, vendor_key) 唯一
    origintype/template/vendor/component
    address_space/address_offset/bit_offset/register_countModbus 地址；非寄存器协议为空
    protocol_address_jsonIEC104 casdu/ioa、DLT645 data_id、IEC61850 object_ref
    wire_type/byte_order原始数据类型与字节序
    enabled/disabled_reason禁用必须有原因，CHECK 约束
    stale_after_ms0 表示继承站默认
    source_import_row_id/legacy_ref导入行追溯与旧表映射

    协议取自 cfg_binding → cfg_channel.protocol，点表不重复存 protocol。

    空值语义：semantic_code、vendor_key 用空串而非 NULL，唯一性靠函数索引 NULLIF(col,'')——“空”不参与唯一，同一设备可以有多条扩展点。这是为适配 ormpp 行映射（它只对算术类型清 NULL 值）而做的显式取舍。

    #6.8 cfg_point_yc（遥测）

    字段说明
    value_typedouble/int64/uint64，CHECK 限定
    scale_factor/offset_value标准值 = 原始值 × scale + offset，scale_factor <> 0
    range_min/range_max工程值量程，越限进 OutOfRange 质量
    deadband变化死区，0 表示逐点上报
    unit/decimals工程单位与显示精度

    表上没有 write_mode、pulse_width_ms，从结构上排除“遥测点可写”。

    #6.9 cfg_point_yx（遥信）

    字段说明
    value_typebool（单点）、int64（状态字）或 string（枚举标签）
    soe记录变位；事件不是第五类遥，仍属遥信
    invert原始位取反（常闭接点）
    enum_json码表 [{raw,label,severity}]
    unknown_policyretain_raw/uncertain/invalid，默认保留原码
    feedback_of_point_id反馈点指回遥控/遥调点

    #6.10 cfg_point_yk（遥控）与 cfg_point_yt（遥调）

    字段YKYT
    value_typebool/int64double/int64
    write_modefixed/direct固定 scaled（不存列）
    fixed_raw_valuefixed 模式必写—
    pulse_width_ms脉冲宽度，0 表示保持—
    scale_factor/offset_value—原码 = (工程值 - offset) / scale
    range_min/range_max—可写工程值上下限
    min_interval_ms最小指令间隔最小调节间隔
    write_group_key共享写寄存器组，同组互斥同左
    feedback_json多判据 [{point_code,criterion,expected,tolerance,order,required}]同左
    feedback_timeout_ms/failure_policy反馈超时与失败策略同左

    遥信反馈点通过 cfg_point_yx.feedback_of_point_id 指回本表，或由 feedback_json 声明多判据；保存校验要求引用存在且指向命令点。

    #6.11 cfg_import_job / cfg_import_row

    cfg_import_job：import_job_id、device_id、binding_id、source_kind、file_name、file_sha256、address_base(zero/one)、idempotency_key（SHA-256(device|binding|sha256)，唯一）、status(parsed/confirmed/applied/failed)、行数统计、提交人与时间。

    cfg_import_row：逐行 vendor_key/vendor_name、point_type（决定写入哪张点表）、target_device_path（空即“目标节点缺失”）、semantic_code、地址与取值列、parse_status/parse_code/parse_message、confirm_state(none/accepted/fixed/rejected) 与确认留痕、resolved_point_id。

    地址占用不单独落表：保存/预览时按 (binding_id, address_space) 实时展开 [offset, offset+register_count) 求重叠，并核对位段；共享通道还应检查相同设备地址的跨绑定冲突。读-读允许；写-写仅当同一非空 write_group_key 且执行端支持互斥才合法，其他写冲突是 error，不能确认绕过。读写交叉作为可确认 warning 写入 import_row.parse_code='address_overlap'，必须逐项说明并确认；无对应导入确认的手工重叠首期拒绝。未排除行的未确认 warning 和任何 error 都阻止应用。

    任务预览不等于工程配置，不增加 config_revision。当前逐行结构不能无损持久化所有 YK/反馈、YX 枚举与 YT 专有字段，首期导入仅接受可完整表达的列，其余返回 Unsupported；完整文件支持须原地扩展既有 DDL、行结构和 ORM，不能只在 Web 内存接受后遗失。

    #6.12 ops_comm_stat_5m / ops_state_log

    • ops_comm_stat_5m：(binding_id, window_start) 主键，请求/成功/超时/错误计数、平均与 p95 时延、最近有效数据时间。采集进程 5 分钟一窗，保留 30 天。
    • ops_state_log：object_kind(device/channel/binding) + object_id + state + since，只在状态变化时写，保留 90 天。最新状态仍在实时库，本表只做追溯。

    #7. 关键流程

    #7.1 保存配置

    BEGIN;
  -- 1. 先锁站根，检查请求 expected_config_revision，不符则结束事务
  SELECT config_revision FROM cfg_device
   WHERE node_kind = 'station' AND device_id = ? FOR UPDATE;
  -- 2. 在锁内读取当前记录、授权并校验候选修改；启用设备强制完整性检查
  -- 3. 直接写工程表（INSERT/UPDATE/DELETE），不做版本复制
  -- 4. 工程实际变化时递增一次；多行保存也只递增一次
  UPDATE cfg_device SET config_revision = config_revision + 1
   WHERE node_kind = 'station' AND device_id = ?;
COMMIT;

    校验失败整事务回滚，页面展示逐项问题；没有“草稿”中间态。新建通信设备默认停用，可先保存档案再配置真实绑定和点；结构、引用始终强制校验，启用或修改已启用路径时要求必需固有点已映射或明确禁用。无变化保存不增加 revision；全体工程写入者遵循先锁站根、再读校验、再写入的顺序，仅在末尾递增不足以避免并发校验竞态。

    当前四遥表的 binding_id 为非空外键，禁用行也必须有真实绑定；未建绑定的固有点只能表示未配置。若要求不接通道就声明某项不支持，需先同步调整既有四表、行结构与 ORM 的来源可空语义，不能插入占位绑定。

    #7.2 热加载

    消费者（采集/策略/实时库）每 N 秒：
  SELECT config_revision FROM cfg_device WHERE node_kind='station' LIMIT 1;
  与内存中的已加载值比较：
    相同 -> 不做任何事
    不同 -> 重新编译运行目录 -> 校验通过后原子切换 -> 记录已加载 revision

    运行目录构建失败时保留旧目录继续运行并上报告警，不部分生效。消费者读取配置的查询必须在一个事务内完成，避免读到“保存到一半”的中间状态。

    #7.3 重复导入与稳定身份

    1. 计算 idempotency_key；已存在则核对 source_kind/address_base，相同返回原任务，不同返回 Conflict。
2. 解析文件写 cfg_import_row，不写点表。
3. 目标节点按 path 匹配（禁止按重名）；未命中即 parse_status='error'。
4. 厂家点按 (binding_id, vendor_key) 命中 -> 复用 point_id 并 UPDATE；
   未命中 -> 分配新 point_id 并 INSERT。
5. 可确认 warning 逐项确认、error 全部修正后，锁站根再锁任务，重查工程与预览哈希并写点表。
6. 同事务回填 resolved_point_id、置 applied 并递增站根一次；applied 重放不重新写点。

    稳定身份只靠唯一键：(path)+code、(binding_id, vendor_key)、(owner_device_id, semantic_code)。

    首期仅合并新增/更新，文件缺席的旧点保留，删除须显式操作。预览内容哈希动态计算用于并发编辑检查，不增加配置版本列；当前任务表未存原提交 revision，重放只能返回当前工程计数，不伪造原提交计数。

    #7.5 点表导入的两条路径

    点表 Excel 只描述"设备的点"，层级关系与每设备通讯参数是 Excel 携带不了的，由两条互补路径覆盖：

    路径 A：整站打包导入（POST /api/station-imports/create）

    上传一个 zip 包（打包文件夹），内含 manifest.json + 每个要导点的设备一个 xlsx：

    station-package.zip
├── manifest.json      // 层级关系 + 通讯参数 + 文件映射（schema: ems-station-package/1）
├── pcs01.xlsx         // 与单设备导入完全相同的点表列格式
└── meter01.xlsx

    manifest.json 结构（字段校验在 station_package_parser，code 规则与界面创建一致）：

    段字段说明
    schemaems-station-package/1版本不匹配整包拒绝
    station.code必填必须与已初始化站根一致（站根不可通过 API 创建）
    devices[]code/name/node_kind/parent_code；device/component 另需 device_type_code/type_version/vendor/model/firmware_version/rated_power_kw；component 必填 source_device_code顺序即创建顺序，parent_code 只能引用已定义节点（天然无环）；unit 挂站根下（parent_code 为空）
    channels[]code/name/protocol/conn_mode/endpoint/poll_interval_ms/timeout_ms/retry_times/max_sessions协议白名单与界面一致（modbus/iec104/dlt645）
    bindings[]device_code/channel_code/device_address/profile_version/can_collect/can_control/can_forward目标必须是 device 节点；同设备同通道唯一
    point_files[]device_code/file/address_base/binding_codebinding_code 省略时取该设备唯一的采集绑定，多个则必须显式指定

    编排语义（station_import_action）：

    1. zip 用 miniz 解包，解压预算与文件数上限同 xlsx 检查（防压缩炸弹），拒绝目录穿越；
    2. manifest 结构校验（引用闭合、类型存在）硬错误整包拒绝，不产生部分生效；
    3. 一个工程事务内：建设备树 → 建通道/绑定 → 对每个点表文件走既有单设备导入（cfg_import_job，status=parsed，含地址占用预检）；
    4. 所有稳定 ID 由包摘要确定性派生（dev-/ch-/bnd- + SHA-256 前缀），重复上传同一包 = 精确重放；
    5. 返回每个设备的 import_job_id/preview_hash/行数统计；确认与落库不自动执行，逐设备走既有 update-row → validate → apply（地址重叠等 warning 必须人工逐行确认，与单设备导入同一套流程）。

    路径 B：单设备导入（已有能力，前端串联即可）

    界面上新建设备（/api/devices/create）→ 配置通讯参数（/api/channels/create + /api/bindings/create）→ 上传该设备 Excel（/api/point-imports/create，multipart：metadata + 单个 xlsx）→ 逐行确认（update-row/validate）→ 应用（apply）。后端已完整实现，无需改动；前端需要做的是把三步串成向导。

    两条路径共用：xlsx 列白名单与解析器（parse_vendor_xlsx）、cfg_import_job/cfg_import_row 逐行确认模型、地址占用与冲突校验、按 vendor_key 幂等更新点行。
