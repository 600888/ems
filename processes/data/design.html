    #数据进程详细设计

    版本：1.0｜日期：2026-10-23｜状态：目标设计，尚未实现常驻进程与管理接口。 本文定义 ems-data 的组装和管理职责；底层记录、并发、来源检查与错误语义引用公共实时访问接口，不另建一套数据契约。

    #1. 设计决策

    新增 C++17 常驻数据进程，将 EMS 调整为采集与上送、数据、存储、策略、Web 五类业务进程。数据进程负责实时后端的初始化与生命周期管理，各业务进程直接通过公共库访问所选后端。

    项目决策
    正常数据访问本进程 RealtimeService → IRealtimeStore → SharedMemoryStore / RedisStore；不经数据进程逐次转发
    共享内存操作系统管理同一共享对象；各进程拥有独立映射、句柄和 C++ 对象
    RedisRedis 服务持有数据；各进程独立连接池，数据进程管理部署契约与接入状态
    后端选择Redis 保持默认，共享内存为同机选项；一个作用域、一个部署代次只使用一个权威后端
    管理通道目标采用内部版本化 gRPC；仅用于接入、诊断及维护，不进入每次实时读写路径
    记录写角色原始点、派生状态、通道状态、命令投影分别指定业务写入者，数据进程不接管所有写入
    消息与历史ZeroMQ 及 MySQL outbox/inbox 继续承担原有职责，不要求经过数据进程
    首期维护停止受影响使用者后切换或重建；不承诺在线热扩容、跨后端双写或自动故障降级

    这里的“对外接口”有两类：供业务代码调用的公共库 API，以及供进程之间使用的管理 API。前者在调用者进程内执行；后者才需要 IPC/RPC。管理进程存在不意味着共享数据必须经过它复制。

    #2. 总体结构与依赖

    公共模型、编解码、门面、存储适配器仍是可复用库，不能依赖 ems-data 业务类。数据进程和其他进程都在各自入口装配这些库；平台映射地址、连接池、虚函数对象和 STL 容器不跨进程传递。协议插件继续使用原有 C ABI，通过采集分发器接入实时库，不要求每个插件单独连接管理服务。

    #3. 职责与写入归属

    数据或行为责任方数据进程的责任
    实测点、设备通信质量、通道状态所属采集实例建立接入信息，按确认的配置与来源事实安装防护字段
    单元/站级聚合、策略状态与告警策略管理后端，不重复计算聚合或运行告警状态机
    命令状态查询投影执行/持久回执协调职责，具体状态字段固定写角色提供存储空间；重建时要求责任方按 MySQL 事实恢复
    已发布配置、来源所有权和代次既有配置发布/持久协调流程读取已确认结果并条件安装，反馈安装版本与缺失项
    历史、审计、配置发布、outbox存储及事实产生进程不改变原链路，不将最新值当作历史事件
    用户身份、站点/资产可见范围Web提供运行诊断；业务鉴权仍在 Web 执行

    每种记录明确唯一业务写角色；多个采集实例按资源所有权分片。初始化记录时先写无有效样本与防护字段，再允许样本更新，不能填默认零值伪造就绪。普通写入方保持 accepted_source_id / accepted_source_epoch / accepted_config_version / write_enabled，不能自行提高 epoch 获取写权。

    数据进程安装防护字段也使用同一记录 CAS，冲突后重读并核对当前持久授权。配置发布版本、授权已安装版本、实例已应用版本分别跟踪；多记录安装逐项完成，不承诺作用域内原子切换。分配来源代次、隔离旧采集实例和控制权仲裁仍由持久协调流程负责。现有来源协调尚未完成，实施时须先明确其权威 Repository 与隔离证据，不能以管理心跳代替。

    #4. 公共库接口与直接访问

    沿用 IRealtimeStore 的 read / compareExchange / erase / readMany / writeMany / info / close。业务使用目标 RealtimeService 的类型化测点和状态接口，具体参数与返回值引用门面契约。

    约束集成要求
    进程内实例每个进程独立创建 store；线程间可按接口约定共享，跨进程不共享对象
    attach业务进程在共享内存模式强制 create_if_missing=false，仅挂接已发布的段
    并发库内部执行进程间锁、完整记录读取与 CAS；禁止进程自行 memcpy 修改业务字段
    批量保留逐项结果与部分成功；不把 readMany 当作同一时刻快照
    时间与错误每次操作有本地 steady deadline，保留 NotFound、NotReady、Conflict、Unknown 等区别
    地址传逻辑记录键，不能传共享段 offset、裸指针或 Redis 原始键给业务算法
    关闭停入口、等待本进程有界在途调用结束，再关闭自身映射/连接；不删除共享对象

    #5. 管理接口与部署描述

    管理服务目标名为 RealtimeAdminService，契约放在 contracts/proto/，首期采用内部 gRPC。接口名和字段为设计约定，仓库尚无对应服务实现。客户端的管理连接与数据连接分开；RPC deadline 转成本地剩余预算，不跨进程序列化 steady_clock 的绝对时间。

    操作输入返回与限制
    GetDeployment逻辑作用域、支持的契约/布局版本当前发布描述；初始化/维护中返回明确状态，不能猜测后端
    RegisterClient实例 ID、启动唯一标识、角色、作用域、已验证的部署/存储代次接入 ID、管理者启动标识、心跳周期；登记不授予设备控制权
    ReportClient接入 ID、加载版本、挂接代次、就绪/维护状态及有界统计接收结果、重核描述或重同步提示；超时只表示状态未知
    UnregisterClient接入 ID、启动标识、退出状态幂等注销，不由注销数量推断可以删段
    GetHealth授权的作用域、分页/条数上限管理、后端、授权、接入状态及诊断；不无限扫描测点
    PrepareMaintenance运维身份、期望部署代次、操作 ID、维护类型维护计划与当前阶段；不立即重建、删段或切换权威后端

    有副作用的管理请求使用稳定操作 ID 与期望代次；响应丢失后先查询操作状态，不盲目重放。维护结果与发布进度须保存到部署管理的持久记录，原子发布运行描述；具体文件/服务适配在实施时固定，不能仅存于会随进程退出消失的内存。首期实际停止进程及最终清理由部署管理执行，管理 API 不提供任意段名删除、SQL 或任意字段写入接口。

    部署描述至少包含：

    字段组字段与含义
    契约schema 版本、支持范围、逻辑作用域、配置/授权应用状态
    部署身份deployment_generation：后端选择及部署清单代次；管理进程普通重启不改变
    存储身份storage_generation：当前后端实例代次；共享段创建后读取实际值，禁止自行推算
    管理身份manager_incarnation：本次管理进程启动标识；只用于接入重登记
    后端定位后端类型、共享段名或 Redis 非敏感端点描述、凭据引用
    兼容与容量布局/schema、平台同步 ABI 要求、段大小、slot 数、分片数、记录与批量上限

    部署管理持久保存预期清单，数据进程检查真实后端后发布当前描述。客户端先核对可信部署配置与描述，再打开后端并复核实际 info()/布局；描述文件和 RPC 应答不能代替后端核验。密钥不出现在描述、心跳或日志中。revision、来源 source_epoch、部署代次、存储代次及管理者启动标识互不替代。

    #6. 启动与接入

    一个 authority domain 对应一个作用域或显式列出的作用域集合；整站和按单元管理二选一，不允许重叠管理。首期每个管理实例只负责一个 domain；Redis 跨主机使用时由部署指定唯一活动管理者，不引入未经验证的自动选主。

    1. 取得管理权：部署锁保证 domain 只有一个管理者；同机使用独立于共享段的 OS 独占锁，并在进程生命周期内持有。跨机 Redis 场景依赖部署隔离旧管理者，单机锁不足以证明唯一性。
    2. 加载清单：校验后端选择、平台、预算、容量和已发布配置；Redis 只连接验证，不由数据进程启动 Redis 服务。
    3. 创建或复用后端：共享段不存在时仅在首次部署或已批准的恢复流程创建；已存在时验证布局/存储代次并复用，不清零现有记录。
    4. 建立授权投影：按持久配置与来源事实初始化缺失记录或协调版本；不能每次重启都重置样本、revision 或来源授权。
    5. 发布接入描述：真实后端通过结构检查后允许兼容客户端挂接，分别显示尚未完成的授权/状态恢复。
    6. 客户端接入：核对描述、以禁止创建模式打开共享段，或创建自己的 Redis 池；构造公共门面，登记实际版本与代次。
    7. 业务就绪：按本角色检查配置、所依赖记录的授权和新鲜度；管理服务就绪不代表设备已在线或策略可控制。

    管理服务发布前，初始化与部署诊断可用，普通客户端有限重试并保持未就绪。共享段 header 的结构 READY 只说明布局和锁已初始化，不代表全部测点、命令投影或业务依赖已恢复。

    #7. 共享内存生命周期

    #7.1 创建、挂接与平台差异

    数据进程是指定初始化者，负责命名、容量、布局检查与常驻持有；业务进程只能 attach/detach。初始化仍遵循公共实时专题的独占创建、结构 READY 和崩溃恢复协议，业务进程不自行 unlink、truncate 或重建。

    Linux 命名共享内存由 shm_open/mmap 创建和挂接，shm_unlink 移除名称；已有映射可能继续存在，直到全部使用者解除映射才释放对象。因此同名删除再创建可能让新旧进程访问不同对象，维护不能以“名称相同”证明数据相同。Linux shm_open/shm_unlink 手册

    Windows 使用命名文件映射，各进程分别取得视图和句柄。数据进程常驻持有映射，所有引用释放后对象不能被视为仍然存在；重新创建须按新存储代次处理。Microsoft 命名共享内存、关闭映射

    当前实现采用 Local 命名空间和默认对象安全属性；Linux 创建权限为 0600。首期部署须保证参与者可访问同一对象、Windows 会话及 Linux IPC/挂载命名空间一致；服务跨会话、不同 OS 账户/容器共享及 ACL 扩展必须另行实现验证，不能仅靠相同段名宣称可用。

    #7.2 管理进程重启

    管理进程退出后，已挂接且共享段仍有效的业务进程可以继续按现有配置与授权直接读写，不要求每次操作探测管理心跳。其前提是实际存储代次未变、锁恢复成功、样本有效，且业务自身依赖的持久状态与控制权仍满足要求。

    管理不可用期间不开放新来源授权、后端切换或新客户端的就绪接入；客户端普通运行重读不依赖管理 RPC。重启的管理者取得唯一管理权后，核对持久部署记录、段内实际 generation、布局和授权，再复用原段；更新 manager_incarnation 并收集重新登记，保留原 storage_generation。

    若对象已丢失、初始化未完成或实际代次无法与可信记录对应，进入恢复待办并停止业务就绪，不因 create_if_missing=true 自动创建空段接替原段。心跳过期和 PID 不存在都不是足以删除共享对象的唯一证据。

    #7.3 扩容、重建与清理

    首期使用维护窗口，不承诺在线热迁移：

    1. 持久登记维护操作及目标部署，关闭新接入，暂停受影响域的新常规调度。
    2. 通知参与者停写并排空本进程在途操作；采样缓冲仍有界，超限和停机历史缺口按原规则报告。
    3. 由部署管理确认相关使用者已退出或已被 OS/容器级隔离；未报告、断线和心跳超时不能当作已停写。无法证明旧实例隔离则中止切换。
    4. 创建带新名称及新 storage_generation 的目标共享段，校验容量与布局；不原地修改仍在使用的锁或记录结构。
    5. 按配置和持久来源事实恢复防护字段；可复制经验证的最后值，但保留原时间/质量并重新判断陈旧。命令投影从 MySQL 恢复，不能推断未知设备动作已完成。
    6. 原子发布新部署描述，重启/重新挂接全部受影响使用者，核对配置、实际代次和角色恢复后开放写入与调度。
    7. 确认旧段不再有使用者，按平台规则清理旧对象；维护失败停在明确阶段，不自动把旧写入者接回新权威域。

    首期不以“客户端收到了新描述”替代旧写入者隔离。共享段内的普通代次字段和 CAS 无法阻止一个仍持旧映射的进程继续操作旧对象；可靠切换依赖上述停止和隔离流程。回滚同样暂停、隔离并发布新的部署代次，不直接恢复旧来源授权。

    #8. Redis 模式与后端切换

    各业务进程用 RedisStore 直接访问权威主节点，独立管理自身连接池和预算。数据进程持有自己的池，负责部署描述、结构检查、授权投影及接入观测；重启它不重启 Redis，也不为其他进程分配或共享连接句柄。

    Redis 拓扑恢复按公共实时专题核对来源、配置及状态，管理健康不能代替每个客户端的实际连接健康。当前适配器配置是单地址/端口模型，不能将设计中的 Sentinel、Cluster 或 TLS 字段宣称为已支持能力。

    切换共享内存与 Redis 沿用第 7.3 节停写、隔离、恢复与发布流程，并执行公共接口的后端迁移约定。同一作用域不得同时接受两个后端的权威写入；Redis 不可用时不自动切换到空共享内存。共享内存跨主机需求应选择 Redis 部署，不自动叠加跨机镜像。

    #9. 通知、历史、控制与 Web

    • 变化提示：由实际更新者在写入后按既有 ZeroMQ 主题发布；数据进程不靠遍历共享段补发每次变化。通知仅唤醒重读，可以丢失；周期性读取和新鲜度检查仍是正确性的基础。管理通知与测点变化主题分开。
    • 历史采样：采集/派生样本产生者发布完整原始事件给存储，最新值更新与发布分别计结果。数据进程不从共享内存轮询生成历史，也不能承诺收到所有中间样本。
    • 控制闭环：写实时值不触发设备动作。MySQL 意图/outbox/inbox、策略仲裁、采集执行与回读链路继续运行；数据进程只维护实时授权投影和状态存储。
    • Web：同机受信任的 Drogon 后端通过公共门面直接读取，与采集、策略使用同一后端。浏览器只访问 REST/WebSocket；Web 的用户权限、分页和展示刷新由 Web 执行，读取锁等待放入有界业务工作池。

    跨主机 Web 无法直接读取本机共享段；首期需要跨机共享实时访问时选 Redis。受限查询网关是另行评审的扩展，不继续默认要求存储进程代理所有 Web 实时查询。

    #10. 权限、健康与故障

    #10.1 直接访问的信任边界

    共享段使用 OS 权限/ACL 限制参与者，管理接口另行认证并区分普通接入、只读诊断和维护权限。公共库执行角色与来源校验，但能直接写共享段的受信进程具有底层修改能力；这不是抵御恶意调用者的逐记录权限边界。

    当前共享内存读操作也会更新进程间锁的同步状态，映射使用读写权限；Web 的“业务只读”不能等同于 OS PROT_READ/只读视图。更强隔离需要额外网关或经验证的布局/权限设计，首期不宣称已支持。

    #10.2 就绪与观测

    状态判断
    管理存活管理循环与独占管理权正常，不等于后端就绪
    后端结构就绪后端可访问、实际代次/布局匹配、必要锁可恢复
    配置授权就绪已确认配置与来源授权按依赖集合安装完成
    客户端就绪各实例报告自身后端、配置与业务依赖有效；报告超时标记未知
    控制就绪策略/采集分别复核持久状态、隔离、质量和能力，数据进程不代为承诺

    指标包含管理重启/接入拒绝、未就绪原因、共享容量、CAS 冲突、锁超时与恢复、代次不匹配、授权安装滞后、Redis 池等待和后端不可用。直接数据访问的调用量/时延由每个进程采集，管理进程自身流量不能代表全系统吞吐；不承诺现有接口已有 slot 使用率扫描或集中指标聚合，须补受限诊断接口。指标避免 point_id 等高基数标签。

    #10.3 故障矩阵

    故障处理与边界
    管理进程退出、后端仍有效已挂接者按原授权访问；新接入和配置/授权变更暂停；恢复复用同代次
    所有 Windows 引用释放或主机重启实时对象丢失，按受控新代次恢复；不能返回默认零值当在线
    初始化者中途崩溃保持未就绪，确认无使用者后管理恢复；客户端不抢先创建
    两个管理者同时启动唯一管理权获取失败者退出，不修改后端；跨机先保证部署隔离
    写入进程持锁崩溃按公共实时后端的 robust/abandoned 锁及映像校验恢复；无法证明有效则隔离报错
    容量满、记录过大返回 ResourceExhausted/InvalidArgument，不覆盖有效数据；进入容量维护流程
    代次/布局不匹配拒绝接入或就绪，不能原地解释为当前布局
    Redis 或共享后端不可用客户端保留结构化错误，按业务规则降级；不自动另选后端
    管理通知/变化提示遗漏重读描述或权威快照，检查配置和新鲜度，不依赖一次通知恢复历史
    维护时旧实例无法确认隔离停止切换，保留维护状态；不因心跳超时清段或开放新写入者

    #12. 当前实现与实施计划

    已有基础尚缺能力
    IRealtimeStore、RealtimeStoreBase、BackendFactory类型化 RealtimeService、可信部署描述及组装校验
    SharedMemoryStore 的创建/挂接、布局/代次检查、平台锁与 CAS常驻生命周期管理、接入登记、维护隔离与清理编排
    RedisStore 的读写、完整替换及错误适配管理者/客户端统一部署校验、授权协调接入
    部分后端与存储核心测试真正多进程生命周期、管理 RPC 与业务端到端验收

    旧采集分发器仍使用旧 RTDB 管理对象，不能把后端库存在视为所有进程已接入。管理接口、配置解析器、类型化门面和常驻入口均为后续工作，本文不声称已经实现。

    阶段交付退出条件
    D1 部署契约domain、角色、描述、代次和接入错误；明确来源协调权威公共样例与布局配置一致，无第二份记录模型
    D2 常驻管理独占管理权、创建/复用、健康、退出业务进程可直接访问；管理重启不清空现有段
    D3 门面与授权公共业务门面、防护字段安装与持久协调接入旧来源拒绝、版本失配拒绝，多点部分完成可观测
    D4 管理与业务接入管理 RPC、客户端、采集/策略/Web 组装与导航配置同套业务 API 可分别运行于 shm/Redis，正常调用无管理转发
    D5 维护恢复停用/隔离、重建、切换、持久进度与清理旧实例未隔离不切换；重建/回滚不复用错误授权
    D6 部署验收Linux/ARM 与 Windows 多进程、故障、容量及性能报告明确支持矩阵、恢复边界和现场预算

    #13. 验收场景

    1. 独立 OS 进程创建与挂接，同名/同代次读到同一记录；业务进程禁止创建，错误布局或代次拒绝接入。
    2. 多进程同时 CAS 同键最多一个成功；批量逐项结果、完整替换、删除重建与业务来源检查保持公共契约。
    3. 停止管理 RPC 或重启管理进程，已挂接业务仍可按原授权直接读写；新接入保持未就绪，恢复后重登记且样本/revision 不被重置。
    4. 并发管理者、初始化崩溃、残留对象、持锁写入者死亡、校验损坏分别得到可观测结果，不用同进程线程用例代替。
    5. 管理进程和全部业务进程分别退出，核对 Linux 残留名称及 Windows 最后引用释放；重新启动不误认旧代次。
    6. 维护时保留一个断联旧写入者，切换必须被阻止；隔离后新段使用新名称/代次，全部使用者重新核验后才能恢复业务。
    7. 切换 shm/Redis、Redis 中断恢复、MySQL 授权读取失败、通知遗漏和容量满，不双写、不自动降级、不以最新值补造历史。
    8. Web 通过同机公共库或 Redis 读取，用户范围仍由 Web 校验；浏览器不能取得共享段句柄，业务只读不宣称物理只读映射。
    9. 按实际点数、频率、记录大小、热点分布、进程数及批大小压测，记录完整门面 P95/P99、锁/池等待、冲突及管理恢复时间；不以 memcpy 或管理 RPC 吞吐代表数据路径性能。

    报告明确实际平台、后端版本、数据规模、通过项与剩余限制。历史丢样、控制持久恢复和配置发布继续执行各自专题验收，不因新增数据进程而视为已解决。
